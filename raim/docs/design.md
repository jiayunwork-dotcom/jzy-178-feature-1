# 设计说明：多模单历元算法与跨历元状态管理

## 1. 单历元层（多模；只含 GPS 时与上一版逐位一致）

### 1.1 多模加权单点最小二乘定位

同一历元的 GPS / Galileo / 北斗伪距**一起**进入解算。各系统系统时彼此有偏差
（接收机钟差相对 GPST、GST、BDT 看到的值不同，即 ISB），因此观测模型为每套
参与系统各保留一个钟差未知量：

```
y = G·dx + ε
G 每行 = [-ux -uy -uz | 钟差列]，钟差列按规范次序 GPS<GAL<BDS 排列，
         本行星所属系统对应列取 1，其余列取 0
W = diag(1/σ_i²)
dx = (GᵀWG)^{-1} GᵀWy
```

参数个数 `p = 3 + k`（3 个位置 + k 套系统各 1 个钟差）。钟差列规范次序固定，
结果与卫星在输入中的排列次序无关。

- 初值取概略位置（回放时沿用上一历元定位结果，首历元用输入或卫星反推的地表点）；
- 收敛判据：位置修正 ‖Δxyz‖ < 1 mm，或迭代 10 轮；
- 输出 ECEF 与经纬度高（WGS84 Bowring 闭式迭代）、**每套参与系统的钟差**、
  实际迭代轮数、每星残差（残差行带所属系统）。
- 顶层 `clock_bias` 字段保持升级前含义：参考钟差，优先取 GPS 列。各系统钟差与
  相对参考系统的 ISB 在每历元结果的 `systems` 数组里给出（见 §5.2）。

**单 GPS 退化**：k=1、p=4，G 就是升级前的 `[-ux -uy -uz 1]`，定位、钟差、
残差、DOP 与升级前逐位一致（兼容性验证见 §6）。

### 1.2 检测

加权残差平方和

```
SSE = Σ_i (r_i / σ_i)²   ~ χ²(n−p) = χ²(n−3−k)   (H0 无故障)
```

阈值 `T` 满足 `P(χ²(n−p) > T) = Pfa`（卡方分位数由 `pkg/chisq` 反解，自研）。

- 冗余自由度 n−p < 1：只有定位、无冗余，结果标 `unavailable`；单 GPS 即 n<5；
- 冗余 ≥1 且 SSE ≤ T：`ok`；
- SSE > T：检出故障。

### 1.3 排除

- 逐星剔除重解。剔除某星后该系统可能少一套钟差列（该星是其系统唯一成员），
  只有**子集仍有冗余**（(n−1)−(3+k′) ≥ 1）的试法才合格；单 GPS 即升级前的
  “剔后剩 4 颗、自由度 0，不能排除”（n<6 无法排除）。
- 对每个合格子集重算 SSE 与对应自由度的阈值；
- **恰有一颗**星剔后通过检验，才认为故障可唯一解释，报 `excluded` 并采用剔星后的干净解；
- 没有任何合格剔法通过（疑似多星故障），或多颗星剔后都通过（无法唯一识别），都按
  `detected` 处理，不使用任何剔星解。

### 1.4 水平保护级 HPL

Brown/Sturza 斜率法：

```
HPL = slopeMax · √λ
```

- `slope_i = ‖(A 前两行)[:,i]‖·σ_i / √S_ii`，A=(GᵀWG)⁻¹GᵀW，取最大斜率；
  多模下 G 含 k 个钟差列，S 与增益矩阵按 `n×p` 实际维度构造；
- √λ 满足 `P(χ'²(dof, λ²) ≤ T) = Pmd`，对非中心卡方 CDF 反解非中心参数（自研）；
- 排除成功后用剩余星几何与子集自由度。几何越差（斜率越大）HPL 越大。

### 1.5 “系统+编号”卫星主键

三套系统编号空间重叠（GPS 3 号与北斗 3 号是两颗不同的星）。全部按星索引的
结构一律使用 `gnss.SatKey{Sys,ID}`：隔离集合、排除结果、每星残差、试排记录、
错误定位。JSON 中：

- 多模历元的卫星引用形如 `{"sys":"BDS","id":3}`，单 GPS 历元与升级前一样只给
  编号、系统字段省略（`omitempty`），旧记录形态不变；
- 升级前落盘状态里隔离 map 的裸编号键（`"3"`）反序列化时解释为 `GPS:3`；
- 隔离列表同时给 `isolated`（编号，升级前字段）与 `isolated_sats`（带系统主键，
  仅多模历元出现），老消费方不受影响。

## 2. 系统时间偏差（ISB）建模：本版最要紧的选型

接收机相对每套系统时的钟差每历元都要处理，有两种做法。**本版选 A。**

### 2.1 方案 A（采用）：每历元自由未知量，不跨历元携带

每套系统的钟差在每个历元都作为新的自由未知量，与位置在同一个最小二乘问题里
无约束解出（即 §1.1 的 k 个钟差列）。历元之间不保存任何钟差/ISB 状态。

**理由**：

1. **检验统计严格**。ISB 被当作自由冗余参数吸收后，SSE 在 H0 下严格服从
   χ²(n−3−k)，卡方检测门限与非中心卡方 HPL 的零假设精确成立；不为省自由度而对
   ISB 的动态特性做任何假设。完好性监测里用“先验”换冗余是危险交易：先验失配
   （真实系统时阶跃、跳变、长期漂移变化）会同时污染位置和检验统计量，虚警/漏检
   口径随之失真。
2. **多模的冗余是净增加**。三系统共视常见 15 颗星以上，只多付 k−1=2 个自由度，
   换来零建模假设与严格统计，划算。
3. **跨历元零状态**。首历元即可估出全部钟差；系统断续可见（某系统几颗星消失再
   出现）时没有陈旧状态可污染；“批量 vs 逐历元一致”“重启续跑一致”两条硬约束
   天然成立——钟差根本不是持久状态，需要持久化和克隆的跨历元状态仍然只有隔离
   集合与告警机。
4. **整系统台阶即被吸收**。Galileo 全部伪距同加一个常数（系统时阶跃）等价于
   GAL 钟差列平移，**在台阶出现的当历元**就被完整吸收：位置、SSE、检测、排除、
   HPL 全部不变，只有 GAL 钟差估计跳到新值。没有过渡历元、没有瞬态。

**吃亏在哪**：

- **稀疏天空下冗余更紧**。三系统各只见 2 颗（共 6 星）时 p=6、dof=0，只能定位
  不能检测；各 3 颗（共 9 星）才能排除。方案 B 借先验伪观测在 5~6 星时仍可能
  检测。多模主要价值在开阔天空，城市峡谷类场景这是实打实的代价。
- **每历元 ISB 估计噪声更大**，不做时间传递/平滑；钟差解的逐历元抖动比携带法大。
- 完全不利用“ISB 短期近似常数”这一真实物理特性。

**台阶行为（验收口径，已用测试钉死）**：因为不携带，Galileo 加常数后**经过
0 个历元即达稳态**——台阶当历元 GAL 钟差完整移动该常数、位置零偏移、SSE 零
变化、不产生任何告警或隔离事件（测试
`TestGalileoConstantStepPositionUnchanged` 逐历元钉住位置、SSE 与钟差台阶）。

### 2.2 方案 B（未采用）：跨历元携带（先验/随机游走/平滑）

把每套系统的 ISB 作为跨历元状态，用随机游走（process noise τ）或带方差先验的
伪观测带到下一历元联合滤波/平滑。

- 优点：稀疏天空下先验提供“伪冗余”，5~6 星也能检测；ISB 估计平滑、可做时间
  传递；长期稳定时参数被历史数据强约束。
- 代价/风险：
  - **首历元与长断续后**先验缺失或陈旧，要么退回自由估计（行为在 A/B 间切换，
    口径复杂），要么用错先验造成台阶期位置偏差与虚警；
  - **真实系统时阶跃**不会像方案 A 那样当历元被吸收：残差先变大（可能误检/误
    隔离该系统的星），再随过程噪声在若干历元内收敛——收敛时间常数由 τ 决定，
    需要额外调参且与真实动力学耦合；
  - 引入 k 份必须持久化、克隆、随批量/逐历元/重启严格一致的跨历元状态；
  - H0 分布不再是干净的中心卡方（先验失配带来非零均值残差），检测门限与 HPL
    的严格性依赖先验正确性。

**什么场景换成 B 更好**：城市峡谷/遮罩严重、单系统可见星长期只有 2~3 颗，
检测冗余比统计严格性更稀缺；或需要稳定的跨历元时间传递输出；或 ISB 已在装机
标定中确认为慢变且可信。届时应把先验方差、过程噪声、阶跃检测/重置逻辑一并
设计，并重新标定台阶响应历元数。当前试飞阶段（开阔多模共视、验收以严格一致
与零瞬态为先）不采用。

## 3. 跨历元状态管理（沿用上一版，隔离主键改为“系统+编号”）

### 3.1 隔离 / 恢复

某历元被唯一排除的星（按 `gnss.SatKey`）进入隔离集合。之后每个历元：

- 隔离星**不参与**定位解；
- 但仍用“含该星的全星解”计算它的恢复检验量（多模全解同样含 k 个钟差列）：
  - 该星标准化残差 |r|/σ 不超单星门限（取与整体卡方阈值一致的 √T，保守）；
  - **且**把它加回后整体 SSE 通过卡方检验；
- 上述两条件须**连续**满足 `isolation.min_epochs` 个历元才解除隔离；
- 期间任一历元不满足，或该星本历元不可见，计数清零重新累计。

解除隔离发生在该历元解算之后，因此该星在“解除”的下一历元才重新参与解算——
这保证“同一历元用排除解、又把同一颗星当正常”不会发生。回放验证（9 星、ts9–ts16 注入
80 m 偏差）：ts9 排除后 ts10–ts20 始终隔离、绝不回拉，偏差撤掉后连续 5 个正常历元，ts21
恢复，故障期间定位始终贴近真值。

隔离集合按系统+编号分别保存：GPS 3 号被隔离不影响北斗 3 号（测试
`TestGPS3BiasIsolationDoesNotTouchBDS3` 钉住）。

### 3.2 告警判定：选型

告警条件是“检测失败（检出无法排除 / HPL > HAL）”。注意：**成功排除单星后采用干净解，
不再告警**——这是上一版“告警跟着坏星反复进出而闪烁”的根因之一；真正需要告警的是
无法安全解释的风险。多模不改变这一口径，告警持续性判定与会话统计与升级前一致。

三种判定方式（运行档 `alert.mode` 可选）：

1. **逐历元快照 `snapshot`**：一个历元超限立即告警，下一历元正常立即撤警。
   - 优点：首次告警延迟最短；缺点：单历元残差尖峰直接变成闪烁告警，误警最多。

2. **持续性窗口 `persistence`**：连续 `confirm_epochs` 个历元超限才拉起，
   连续 `clear_epochs` 个正常才撤除；窗口内一次反复会打断计数。
   - 优点：尖峰被滤掉、误警最少；缺点：真实故障的首次告警最多滞后 `confirm_epochs` 个历元。

3. **组合 `combined`（默认，内置三档均采用）**：普通超限走持续性窗口；
   **恶劣超限**（SSE ≥ `gross_factor×T` 或 HPL ≥ `gross_factor×HAL`）立即告警，
   撤警仍走窗口。
   - 既对“明显危险”保持即时响应，又对“边界附近的抖动”保持迟滞。

> 结论：三者不是互斥替代，而是**延迟—误警—可用率**的权衡。内置档选 `combined`，
> 把“立即响应恶劣故障”和“滤掉边界闪烁”同时拿到；对延迟极度敏感的阶段可下调
> `confirm_epochs` 或改用 `snapshot`，对误警极度敏感的监测可只用 `persistence`。

由 `cmd/replaydemo` 生成（该演示为纯 GPS，升级前后输出逐字节一致），完整 JSON 见
[replay_results.json](replay_results.json)。

| 场景 | 指标 | snapshot | persistence | combined |

| | 告警片段（误警） | **3** | 0 | 0 |
| | 服务可用率 | 0.997 | **1.000** | **1.000** |
| **单历元尖峰**（3 个残差尖峰，无真故障） | 告警片段（误警） | **4** | 0 | 0 |
| | 服务可用率 | 0.996 | **1.000** | **1.000** |
| **持续中等故障**（双星，可检出不可排除、非恶劣） | 首次告警延迟（历元） | 4 | 6 | 6 |
| | 告警片段 | **3（闪烁）** | 1 | 1 |
| | 服务可用率 | 0.917 | **0.950** | **0.950** |
| **恶劣故障**（双星大偏差，SSE≥3×阈值） | 首次告警延迟（历元） | 1 | 3 | **1** |

\* 组合模式在恶劣故障上当历元即告警，因此比“等满 3 历元”的持续性方式多覆盖了故障开头
2 个历元的告警（更保守），可用率略低但响应更及时。

读数：

- **首次告警延迟**：快照恒为 1；持续性对中等故障需等满窗口（本例 6，因噪声使前两个超限
  历元未连续）；组合对**恶劣**故障回到 1，对中等故障与持续性一致（有意迟滞）。
- **误警次数**：快照在纯噪声/尖峰下分别产生 3、4 个误警片段（正是试飞组看到的闪烁），
  持续性与组合为 0。
- **可用率**：持续性/组合在无故障与尖峰场景保持 100%；快照因误警受损。真实故障期间
  告警越保守可用率越低，这是为安全付出的代价；组合在“恶劣故障即时告警”和“其余时间
  高可用”之间取得平衡。

### 3.4 误警口径

- 在线服务（`session.Stats.FalseAlarms`，无地面真值）：一个告警片段内**从未识别出任何
  故障**（无检测/排除事件）才算误警——这是接收机自身能做的保守统计。
- 回放分析（`replaydemo`，知道注入真值）：告警片段与“真实持续故障窗口”不相交才算误警。
  单历元尖峰触发的快照告警因此被正确标为误警。

## 4. 会话与持久化

- 会话创建时绑定一个运行档；可一次批量提交（≤3600 历元，整段原子、任一历元非法整段拒收），
  也可逐历元提交；两条路径调用**同一个 `Service.Step`**，逐历元结果严格一致。
- 时间戳：与上一历元相同 → 409 拒收、状态不推进；倒退 → 422 拒收。
- 持久化的跨历元状态仍是**隔离集合及计数、告警机、统计、last_ts、全部记录**；
  ISB 不携带（§2），没有新增任何跨历元状态。状态以 JSON 原子写（临时文件 +
  rename）落盘；重启后从最后历元继续，与一口气跑完逐项相等
  （多模验证：`TestMultiBatchEqualsIndividual`、`TestMultiRestartResumeEqualsContinuous`）。
- 每个历元记录都带所用档名、Pfa/Pmd/HAL、当时卡方阈值与自由度。
- **升级前会话文件直接兼容**：读入时隔离 map 的裸编号键解释为 GPS:3；已落盘的
  历元记录原样保留、绝不重算或改写，新历元在其后正常推进
  （`TestLegacySessionFileContinues`）。

## 5. 输入输出约定

### 5.1 输入校验（错误指到具体字段）

在升级前全部校验基础上新增两条：

- **系统标识不认识**：`sys` 不在 `GPS/GAL/BDS`（大小写不敏感，兼容 G/E/C、
  GALILEO/BEIDOU 等别名）→ 拒收，指到 `satellites[i].sys`；
- **同一系统内编号重复** → 拒收，指到 `satellites[i].id`；**跨系统同号不算重复**，
  GPS:1 与 GAL:1 同时合法。

其余沿用：不足 4 颗星、多模时星数不足 3+系统数、坐标/伪距 NaN 或无穷、σ≤0、
概略位置近地心、卫星共面等几何奇异，均返回带字段路径的错误；批量提交一律再带
历元下标（如 `epochs[3].satellites[1].sys`）。无 `sys` 字段的星按 GPS。

### 5.2 每历元的多系统输出（仅多模历元出现）

`systems` 数组按 GPS、GAL、BDS 次序给出本历元可见的每套系统：

```json
"systems": [
  {"sys":"GPS","participated":true,"visible":7,"used":7,"clock_bias":12.3,"inter_system_bias":0},
  {"sys":"GAL","participated":true,"visible":7,"used":7,"clock_bias":45012.1,"inter_system_bias":44999.8},
  {"sys":"BDS","participated":true,"visible":7,"used":7,"clock_bias":-11987.0,"inter_system_bias":-11999.3}
]
```

- `participated`/`used`：该系统是否实际参与**报告的定位解**（排除后按干净子集
  计；可见但该系统唯一星被剔时 `participated=false`）；
- `clock_bias`：该系统的接收机钟差（米）；`inter_system_bias`：相对参考系统
  （优先 GPS）的偏差。某历元不可见的系统不出现在数组里——“是否参与/可见”一眼可辨。
